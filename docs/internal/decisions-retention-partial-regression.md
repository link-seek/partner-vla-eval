## 决策 1：recording sqlite 保留多久

### 事实

| 项 | 数值 |
|---|---|
| 单 task 50 集 sqlite | **约 3.1 MB**（当前 12 集 772K 线性外推） |
| 一次评测活动（5 task × 2 难度 × 2 模型） | 约 **62 MB** |
| 机器 `/data` | 1007G，已用 557G，**剩 400G** |
| OBS 标准存储 | ¥0.099/GB/月 → 62MB ≈ **¥0.006/月** |

**关键点**：sqlite 已经随 `matrix/` 传到 OBS 了（不是只存在机器上）。所以"保留"的实际成本几乎为零，
真正要定的是 **OBS 侧的生命周期策略**。

### 为什么值得留

sqlite 是**唯一**能：
1. 重新 `vla-eval export`（重算 aggregate，或补上后来才想到的指标）
2. 逐集复核（哪一集失败、卡在哪一步、`failure_detail` 是什么）
3. 崩溃后救援（今天已验证：从在写的 sqlite 捞出 8/12）

蒸发的只有 explain 能力——aggregate 留不住"为什么失败"。

### 选项

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **A（建议）全留** | OBS 不设过期；本地 `results/` 每轮清空（现行为） | ≈¥0.006/月 | 无实质代价 |
| B 留 90 天 | OBS 生命周期规则 90 天 | 更省（但本来就近乎免费） | 3 个月后无法复核逐集 |
| C 只留 aggregate | 上传时排除 `*.sqlite` | 0 | 失去救援与逐集复核 |

### 建议：A

理由：**成本可忽略（每月不到一分钱），而它是"复核能力"的唯一载体**。真要大扫除，
按"活动归档"整包删（比如 2026 年以前的），而不是逐轮删 sqlite。

## 决策 2：partial（n<50）结果进不进榜

### 事实

现状：`leaderboard` schema 要求 `n`，但没有"目标 n"概念；榜单一格和另一格 n 可以不同，
读者看不出来。而 n 不同的误差差很多：

| n | 95% CI 半宽（p=0.9） |
|---|---|
| 3 | ±33.9pp |
| 10 | ±18.6pp |
| 25 | ±11.8pp |
| 50 | ±8.3pp |

**n=12 的 66.7% 和 n=50 的 66.7% 是两件完全不同的事**（前者真值可能 33%~100%）。

### 选项

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A（建议）只进附录** | 榜单只收 n=50 满格；partial 放 `docs/data/partial/`，报告里标"进行中 n=12/50" | 榜单干净，不会被半截数误导 | 早期信号不能立刻展示 |
| B 进榜但标 n | 榜单加一列 n，partial 用灰色显示 | 能看到在跑 | 有人会拿 n=12 去比 n=50 |
| C 什么也不留 | 崩了就丢弃 | 最简单 | 已经花的钱白花 |

### 建议：A + 一条门禁

- 榜单文件里 **n 必须等于协议的 `expected_n`（50）**，否则 `check_leaderboard.py` 报错
- partial 结果落到 `docs/data/partial/<model>-<task>-n<N>.json`，带 `partial: true` 与 `n_target`
- 汇报时可以说"中途读数 8/12"，但**不进表**

理由：我们对外的主张是"可比"，而 n 不同根本不可比。留附录既保住信息，又不污染排名。

## 决策 3：回归测试频率

### 先厘清它要防什么

门槛已经钉死：镜像 tag、harness ref、种子、分片数。那还剩什么会漂？

1. 镜像被重打（同 tag 不同内容）——**这是最大风险**，我们目前只有 tag 没有 digest
2. 上游 harness 行为变化（我们钉 ref，但 base 镜像里的依赖会变）
3. 机器层面（显卡驱动、CUDA）——同机风险低，换机会有

### 关键未知：同种子重跑是否逐集一致

这决定回归测试能不能**便宜地做**：

- 如果**确定**（同种子同结果）→ 回归只需 **3 集**（¥6–8）：结果不一致就说明栈变了
- 如果**不确定**（物理/线程非确定）→ 回归必须 50 集才有统计意义（¥104–137/次）

**我们手上有一份反例线索**：CogACT `place_phone_stand` 两轮 8/50(16%) vs 6/50(12%)。
若两轮用的是同一批种子，这 4pp 差异就说明**不完全确定**——但当时可能种子集不同，无法定论。

### 选项

| 方案 | 做法 | 成本 | 覆盖 |
|---|---|---|---|
| **A（建议）先做一次确定性实验** | 1 task × 3 集 × 3 轮，同种子重跑，看是否逐集一致 | **约 ¥20**（3 轮 × 0.2h） | 一次性，决定后续策略 |
| B 按月全量 | 每月 1 task × 50ep | ¥105/月 | 能检测 ≥8pp 漂移 |
| C 按变更触发 | `versions.yaml` 或镜像 rebuild 时自动跑 1 task × 50ep | 每年约 ¥300（假设每季改一次） | 精准命中风险点 |
| D 每周 | 每周 1 task × 50ep | ¥420/月 | 过度 |

### 建议：A → 然后 B+C 组合

1. **先花 ¥20 做确定性实验**（3 集 × 3 轮）：
   - 若逐集完全一致 → 回归改成**每次镜像/bin 变更时跑 3 集**（¥8），几乎零成本
   - 若不一致 → 回归用 **1 task × 50ep，按变更触发**（C 方案），不做月度例行
2. **长期防御重点其实是 digest**：把 `serve_image`/`bench_image` 从 tag 改成 `tag@sha256`，
   一次做完就消灭"同 tag 不同内容"这个最大风险源（对应整改计划 A1/P0-3）

## 三个决策的联动

```
决策 1（留 sqlite）
   └─ 使决策 2 的 partial 可追溯（附录里的数能回查逐集）
   └─ 使决策 3 的回归可对照（同种子逐集比对需要 sqlite）

决策 3（回归）依赖决策 1：没有 sqlite 就无法"逐集比对"确认确定性
```

所以顺序上：**先定 1（几乎零成本，建议 A）→ 再做 3 的确定性实验 → 2 按 A 直接实施**。
